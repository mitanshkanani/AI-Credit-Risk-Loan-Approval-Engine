# M4 – XGBoost (gradient boosting challenger): implementation plan

## Goal
M3 (LightGBM) clearly beat Logistic Regression. M4 answers the model strategy's question:
**is that result real, or specific to one library and its settings?**
- XGBoost about equal to LightGBM → the boosting gain is real, and we keep the faster/simpler of the two.
- XGBoost clearly better (> +0.005 ROC-AUC) → it becomes the main candidate.
- XGBoost clearly worse → M3 stays; check why.

## What is different from LightGBM
Same idea (shallow trees built one after another, each correcting the previous trees' mistakes),
different engine:
- XGBoost grows trees **level by level** (`max_depth` controls size); LightGBM grows **leaf by leaf** (`num_leaves`).
- XGBoost regularises with `min_child_weight` (minimum sum of hessians per leaf), `gamma` (minimum
  loss reduction to split), and L1/L2 penalties `reg_alpha` / `reg_lambda`.
- `tree_method="hist"` uses histogram binning like LightGBM.

## Data and versions (identical to M1-M3)
A: 189 features · B: 147 (no LendingClub grades; **deployable**) · fit on train, early-stop and choose
on validation, **test sealed**.

## Training setup
XGBoost core API (`xgb.train` + `DMatrix`), `objective="binary:logistic"`, `tree_method="hist"`,
early stopping on **validation AUC** after 100 rounds without improvement (max 5,000 rounds),
`seed=42`, all CPU threads.

## Hyper-parameter search: random search, 40 settings per version (learning rate 0.05)
| Parameter | Range | Meaning |
|---|---|---|
| `max_depth` | 3-10 | tree depth |
| `min_child_weight` | 1-200 (log) | minimum hessian sum per leaf (≈ minimum loans per leaf / 0.14) |
| `subsample` | 0.5-1.0 | share of loans per tree |
| `colsample_bytree` | 0.4-1.0 | share of features per tree |
| `reg_lambda` | 0.001-10 (log) | L2 penalty |
| `reg_alpha` | 0.0001-10 (log) | L1 penalty |
| `gamma` | 0-1 | minimum loss reduction to split |

Trial 0 = XGBoost defaults (depth 6, min_child_weight 1, subsample 0.8, colsample 0.7).
**Selection rule:** highest validation ROC-AUC; within 0.0005 prefer the smaller `max_depth`.

## Follow-up experiments (same as M3)
1. Learning rate 0.02: kept only if validation AUC improves by at least 0.0005.
2. `scale_pos_weight = #repaid / #defaults` (XGBoost's class weighting).
3. Monotonic constraints on B (FICO ↓, DTI ↑, income ↓, 60-month ↑, inquiries ↑, utilisation ↑) → `B-mono`.

## Evaluation
- Shared report card; comparison with M1, M2 and **head-to-head with M3** (ROC-AUC, Brier, training time).
- Rank agreement (Spearman) between M3-B and M4-B; learning curve; decile calibration;
  approval-rate vs bad-rate curve (M0, M1-B, M3-B, M4-B); 36 vs 60-month segments; A minus B.
- SHAP (XGBoost's built-in `pred_contribs`) on 20,000 validation loans: top 20 features, compared
  with M3's ranking, plus one example applicant.

## Where it runs: Kaggle only (private)
- Dataset `mitanshkanani/credit-risk-model-inputs` gets a **new version** that adds M3's validation
  predictions (still train + validation only, no test).
- Kernel `mitanshkanani/credit-risk-m4-xgboost`: runner generated by `kaggle/build_runner.py`
  (embeds notebook, `evaluation.py`, leaderboard).
- XGBoost is not installed locally, so the **smoke test also runs on Kaggle** (3 settings, 60 rounds),
  then the full run.
